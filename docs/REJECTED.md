# Rejected Changes and Features

Everything tested and **not** adopted, grouped by what it touched. Keeping this
list is what prevents re-testing the same idea every few months; it is the
negative half of the ledger, the twin of [DECISIONS.md](DECISIONS.md).

**Before re-opening anything here, read
[the re-opening rule](AB_TESTING.md#how-changes-are-validated).** A rejection is
re-opened only with a *stated mechanism*, written down before the run: what
changed in the model, the data or the measurement that would make the answer
different now. "A lot has changed, maybe it behaves differently" is not a
mechanism. Per-measurement noise is a few tenths of a EUR/MWh, so re-testing
enough rejected entries will make some of them "pass" by chance.

**Two rules for the rows themselves.** A row must be readable without
`experiments/` — that directory is scratch and is not committed — so it carries
its own numbers: grid, snapshot, arms, deltas, how many measurements were
favourable, and for a feature, whether it was frozen across the forecast window
or recomputed per day
([AB_TESTING.md](AB_TESTING.md#horizon-honesty-measure-only-what-production-can-know)).
A rejection measured on a leaky arm is worth more than one measured honestly — it
closes the route — but only if the entry says so. And a verdict is **scoped to the model it was measured on**: when a
feature list changes materially, rows measured against the old list may no
longer say what they appear to say (see
[AB_TESTING.md](AB_TESTING.md#how-changes-are-validated)).

Where a round produced a finding worth more than a table row, the row links to
[FINDINGS.md](FINDINGS.md).

The 15-column `TROUGH_FEATURE_COLUMNS` / 14-column `MIN_FEATURE_COLUMNS` are a
local optimum in both directions: nothing excluded has replicated when added
back, and nothing kept has survived a leave-one-out as droppable.
